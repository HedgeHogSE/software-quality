# Техническое задание: разработка приложения для моделирования качества ПО на основе системной динамики (модель ISO)

## 1. Общая информация

**Название проекта:** «Моделирование качества программного обеспечения на основе системной динамики (модель ISO)».

**Цель разработки:** создать настольное приложение на Python, воспроизводящее математическую модель качества программного обеспечения из лабораторной работы «Качество ПО.docx».

Приложение должно позволять задавать параметры модели, рассчитывать динамику характеристик качества ПО посредством численного решения системы дифференциальных уравнений, учитывать внешние возмущения и визуализировать результаты моделирования.

**Целевые операционные системы:** Windows, Linux, macOS.

**Основной язык:** Python 3.11 или новее.

**Основные библиотеки:**
- `tkinter` / `ttk` — графический интерфейс;
- `numpy` — численные вычисления и работа с массивами;
- `scipy` — решение системы дифференциальных уравнений;
- `matplotlib` — построение графиков;
- `pytest` — автоматизированные тесты.

При выборе конкретных библиотек и методов необходимо отдавать предпочтение простым и надёжным решениям, не усложняя архитектуру без необходимости.

## 3. Математическая модель

### 3.1. Основной принцип

Приложение должно моделировать изменение состояния системы во времени.

Общий вид системы:

\[
\frac{du_i(t)}{dt}=F_i(t,\mathbf{u}(t),\mathbf{p}),
\]

где:

- \(u_i(t)\) — отдельная переменная состояния;
- \(\mathbf{u}(t)\) — вектор всех переменных состояния;
- \(\mathbf{p}\) — параметры и коэффициенты модели;
- \(F_i\) — правая часть соответствующего дифференциального уравнения;
- \(t\) — время.

Используй этот вид как общую математическую структуру, но сами функции \(F_i\) должны быть реализованы по оригинальным формулам из лабораторной работы.

### 3.2. Переменные состояния

В системе должны присутствовать все 28 переменных, перечисленных в исходной модели:

`u5`, `u24`, `u25`, `u26`, `u27`, `u28`, `u54`, `u55`, `u56`, `u107`, `u108`, `u109`, `u110`, `u111`, `u112`, `u113`, `u114`, `u115`, `u116`, `u117`, `u118`, `u119`, `u120`, `u121`, `u122`, `u123`, `u124`, `u125`.

Порядок переменных в вычислительном векторе должен быть зафиксирован и документирован. Один и тот же порядок должен использоваться при задании начальных условий, решении системы и интерпретации результатов.

### 3.3. Реализация уравнений

Для каждой переменной необходимо реализовать отдельную правую часть уравнения либо организовать вычисление всей системы в одном хорошо структурированном модуле.

Требования:
- математические выражения должны соответствовать исходному документу;
- все функции и коэффициенты должны иметь однозначные определения;
- взаимосвязи между переменными должны быть сохранены;
- нельзя пропускать уравнения или заменять их константами;
- нельзя подменять нелинейные зависимости линейными ради упрощения;
- необходимо учитывать все слагаемые, множители, знаки и зависимости от времени;
- код должен позволять сопоставить каждое уравнение с исходной формулой.

Если в оригинальной формуле есть деление на переменную состояния, необходимо отдельно обработать возможность нулевого знаменателя. При этом нельзя молча заменять формулу произвольным значением: программа должна сообщить об ошибке или применить только математически обоснованную стратегию.

### 3.4. Функции модели

Реализуй все функции, используемые в исходных уравнениях.

В частности, проверь наличие линейных, квадратичных, кубических и других зависимостей, а также всех функций времени, указанных в документе.

Для каждой функции:
- сохрани оригинальный вид;
- реализуй вычисление в отдельной функции Python либо в эквивалентном структурированном виде;
- документируй аргументы;
- проверь корректность вычислений на контрольных значениях;
- предусмотрительно обрабатывай недопустимые аргументы и нечисловые результаты.

Не ограничивайся только несколькими примерами функций из документа. Реализовать необходимо полный набор функций, используемых всеми 28 уравнениями.

### 3.5. Коэффициенты модели

Все коэффициенты, присутствующие в исходных уравнениях, должны быть вынесены в единое место конфигурации.

В том числе проверь наличие коэффициентов вида `Fak1`, `Fak2` и остальных коэффициентов исходной модели.

Для каждого коэффициента должны быть определены:
- исходное обозначение;
- значение по умолчанию;
- источник значения;
- назначение, если оно установлено в исходном документе;
- возможность изменения через интерфейс, если это предусмотрено исходной моделью.

Не назначай произвольные значения коэффициентам, для которых исходные значения не установлены. Такие параметры должны быть явно помечены как требующие определения.

## 5. Численное решение системы

Для решения системы используй `scipy`.

В исходной лабораторной указана функция `ode`, основанная на методе Рунге — Кутты. Приоритетный вариант — воспроизвести подход исходной работы с помощью подходящего интегратора из `scipy.integrate.ode`.

Допускается использовать `scipy.integrate.solve_ivp`, если это обеспечивает более надёжную реализацию и выбранный метод численного интегрирования документирован. При этом математическая модель должна оставаться неизменной.

### 5.1. Входные данные решателя

Решатель должен получать:
- все начальные значения переменных состояния;
- параметры модели;
- функции возмущений;
- начало и конец интервала моделирования;
- настройки точности и интегрирования.

### 5.2. Результаты

Результат должен содержать:
- массив времени;
- рассчитанные значения всех 28 переменных в каждый момент времени;
- сведения об успешности или неуспешности расчёта;
- диагностическое сообщение при возникновении ошибки.

Результаты должны храниться в структуре, позволяющей строить графики без повторного вычисления системы.

### 5.3. Проверки корректности

Обрабатывай:
- некорректные начальные значения;
- неверные параметры;
- деление на ноль;
- переполнение;
- `NaN` и бесконечности;
- ошибки численного интегрирования;
- слишком маленькие или некорректные временные интервалы.

Если решение не получено, интерфейс должен сообщить об ошибке и не отображать предыдущие результаты как новые.

Не изменяй значения состояния искусственно, чтобы графики выглядели плавными или ожидаемыми.

## 6. Графический интерфейс

Приложение должно быть полноценным настольным приложением на `tkinter` с использованием `ttk`.

Интерфейс должен быть простым, аккуратным и пригодным для демонстрации лабораторной работы.

Предусмотри следующие основные разделы.

### 6.1. Вкладка «Параметры»

На вкладке пользователь должен иметь возможность просматривать и изменять доступные параметры модели.

Требования:
- отображение всех переменных состояния;
- ввод начальных значений;
- отображение коэффициентов модели;
- ввод временного интервала;
- ввод настроек численного решателя, если они доступны;
- кнопка запуска моделирования;
- кнопка восстановления исходных параметров;
- валидация введённых значений.

Для 28 переменных не обязательно использовать 28 отдельных больших полей на одном экране. Можно организовать таблицу или прокручиваемый список.

Все параметры должны иметь понятные подписи, но оригинальные обозначения `u5`, `u24` и т. д. должны сохраняться.

### 6.2. Вкладка «Графики»

На вкладке необходимо показывать динамику характеристик модели.

Требования:
- графики значений переменных в зависимости от времени;
- выбор отображаемых переменных;
- возможность показать несколько переменных одновременно;
- легенда;
- подписи осей;
- заголовок;
- масштабирование и навигация по графику;
- корректное отображение отрицательных и положительных значений;
- обновление графиков после успешного расчёта.

Поскольку переменных 28, не следует без необходимости размещать все графики в одном перегруженном изображении. Предусмотри выбор переменных и возможность отображать группы графиков.

Если в исходном документе есть дополнительные правила группировки характеристик, используй их.

### 6.3. Вкладка «Возмущения»

На этой вкладке отображай все предусмотренные моделью внешние возмущения.

Пользователь должен видеть:
- название возмущения;
- его математическую функцию или обозначение;
- изменение во времени;
- график на интервале моделирования.

Графики должны рассчитываться по тем же функциям, которые фактически используются при интегрировании системы.

### 6.4. Отображение состояния системы в контрольные моменты

В лабораторной работе для каждой реализации приведены результаты в пяти временных точках:
1. Начальный момент.
2. Первая четверть временного интервала.
3. Вторая четверть.
4. Третья четверть.
5. Конечный момент.

Реализуй возможность просмотра значений всех переменных в этих точках.

Если интервал равен \([t_0,t_1]\), контрольные моменты:

\[
t_k=t_0+\frac{k}{4}(t_1-t_0),
\quad k=0,1,2,3,4.
\]

Используй значения численного решения в этих точках. Если решатель не вычислял их непосредственно, получай значения с помощью корректной интерполяции или включи контрольные точки в запрашиваемую сетку вывода.

Для каждой точки отображай таблицу значений переменных состояния.

### 6.5. Состояние приложения

Интерфейс должен показывать:
- готовность к расчёту;
- выполнение расчёта;
- успешное завершение;
- ошибку вычислений;
- наличие актуальных результатов.

Пока выполняется длительный расчёт, интерфейс не должен выглядеть полностью зависшим. При необходимости выполняй вычисления в отдельном рабочем потоке, не обращаясь к элементам `tkinter` из этого потока.

## 10. Тестирование

Обязательно создай автоматические тесты.

### 10.1. Тесты функций

Для каждой функции модели проверь:
- вычисление на нескольких контрольных значениях;
- правильность знаков и коэффициентов;
- поведение на границах допустимой области;
- обработку недопустимых входных значений.

Эталонные значения должны быть рассчитаны по исходным формулам, а не взяты из самой тестируемой реализации.

### 10.2. Тесты возмущений

Проверь:
- правильность вычислений в начальный момент;
- значения в нескольких промежуточных точках;
- соответствие графика исходной функции;
- корректную передачу возмущений в правые части уравнений.

### 10.3. Тесты уравнений

Для всех 28 уравнений:
- проверь наличие реализации;
- сопоставь код с исходной формулой;
- проверь порядок переменных;
- проверь правильность знаков и коэффициентов;
- проверь отсутствие случайных пропусков слагаемых.

### 10.4. Тесты решателя

Проверь:
- корректное решение простой тестовой системы;
- успешный расчёт полной модели при допустимых исходных данных;
- правильное количество переменных в результате;
- соответствие длины массива времени и массива состояний;
- конечность вычисленных значений;
- корректную обработку ошибки интегрирования.

### 10.5. Тесты пяти реализаций

Проверь возможность создать пять независимых запусков и сохранить результаты каждого.

Изменение параметров одной реализации не должно незаметно менять параметры других реализаций.

### 10.6. Проверка математической точности

Если в исходном приложении доступны эталонные числовые значения или графики, сравни результаты новой реализации с ними при совпадающих параметрах и настройках.

Если эталонные значения отсутствуют, не утверждай, что результаты полностью совпадают с оригинальной программой. В этом случае выполни проверку по исходным формулам, контрольным вычислениям и сходимости численного решения.
